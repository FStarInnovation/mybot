План архитектуры проекта

Роли и зоны ответственности команд и компонентов
	•	Backend (Laravel Cloud) – Команда бэкенд-разработчиков:
	•	Разработка основного API сервера на Laravel для обслуживания запросов от всех клиентов (Web, Telegram, WhatsApp).
	•	Реализация REST API и (при необходимости) WebSocket для отправки и получения сообщений чата.
	•	Управление аутентификацией пользователей, сессиями, биллингом и правами доступа (особенно для платных уведомлений и premium-функций ассистента).
	•	Имплементация API-методов для инструментов, вызываемых LLM (например, эндпоинты для парсинга веб-страниц, выполнения поисковых запросов, и других функций, требующих внешних ресурсов).
	•	Взаимодействие с системами памяти: запрос и обновление короткой памяти (Upstash Redis) и долгой памяти (Neon/Supabase/Qdrant) по необходимости для каждого запроса пользователя.
	•	Интеграция с внешними сервисами (Telegram Bot API, WhatsApp Business API) для приема/отправки сообщений и уведомлений.
	•	Обработка результатов от AI-модели (LLM): форматирование ответа, пост-обработка (например, фильтрация нежелательного контента), логирование результатов.
	•	Обеспечение масштабируемости: управление очередями запросов к LLM (например, через очереди Laravel Horizon или аналог) чтобы избежать перегрузки AI-сервиса.
	•	Платформа AI/ML (RunPod LLaMA3 + Tools) – Команда ML/AI-инженеров:
	•	Разворачивание и поддержка модели LLaMA3 (Large Language Model) на платформе RunPod (или аналогичном GPU-хостинге) для обработки запросов в режиме реального времени.
	•	Настройка окружения для LLM с возможностями tool calling: интеграция механизмов, позволяющих модели вызывать внешние инструменты при необходимости (например, доступ к поиску, парсингу сайтов, базе знаний и т.д.).
	•	Встроенная библиотека Jina Embedding (или альтернативы) для генерации эмбеддингов текста: используется моделью или вспомогательным сервисом для превращения текста (запросов, контекста) в векторное представление для поиска по памяти.
	•	Использование сервера Tornado (Python) для хостинга API вокруг LLM: обеспечивает низкую задержку и возможность асинхронной обработки (важно для одновременной работы с моделью и инструментами, парсинга и пр.).
	•	Реализация логики парсинга внутри AI-платформы: возможность запускать Puppeteer/Playwright (headless-браузер) для получения содержимого веб-страниц и BeautifulSoup для извлечения текста/данных из HTML. Эти инструменты могут вызываться моделью (как внешние функции) или предварительно бэкендом.
	•	Интеграция с OpenEvolve (если планируется): внедрение агентной логики, которая помогает модели итеративно улучшать ответы или выполнять сложные многошаговые задачи (например, написание и оптимизация кода). Эта часть должна быть изолирована и вызываться только при соответствующих запросах.
	•	Обеспечение гибкого взаимодействия с Backend: модель должна уметь принимать входные данные (запрос пользователя + контекст), а при необходимости делать вызовы по определенным API-эндпоинтам Laravel (инструменты) и получать ответы, прежде чем сформировать финальный ответ.
	•	Оптимизация производительности LLM: загрузка модели в память GPU, настройка квантизации/шардирования если нужно, мониторинг времени ответа. Обработка ошибок инструментов (например, таймаут при парсинге) и обеспечение, что модель корректно реагирует на неудачные вызовы.
	•	Фронтенд (Web-клиент на SvelteKit + TanStack Query) – Команда фронтенд-разработчиков:
	•	Разработка пользовательского интерфейса веб-приложения на SvelteKit для взаимодействия с LLM-ассистентом (чат-интерфейс, отправка вопросов, отображение ответов, уведомлений и пр.).
	•	Использование TanStack Query для эффективного управления состоянием данных на клиенте: выполнение запросов к API Laravel, кэширование ответов (например, истории диалога, результатов запросов) и обновление UI при новых данных.
	•	Обеспечение в реальном времени обновления UI для ответов ассистента: поддержка streaming-ответов (постепенная печать сообщения, если API это позволяет) или индикация “typing…” от ассистента.
	•	Реализация удобной навигации и UX: настройки профиля пользователя, просмотр истории запросов (если храним локально или краткосрочно), управление подписками на уведомления.
	•	Интеграция (или оценка интеграции) готового интерфейса AG-UI: анализ возможностей существующего UI для LLM-диалогов. Задача: решить, будет ли использоваться AG-UI как основа (если он предоставляет улучшенные функции: напр. управление многими диалогами, подсветка источников, и др.) или же оставить кастомный интерфейс на SvelteKit. Команде фронтенда нужно прототипировать интеграцию AG-UI и оценить трудозатраты/выигрыши.
	•	Взаимодействие с сервисами уведомлений: возможна реализация в UI настроек для пользователя – как он хочет получать ответы (например, push-уведомление, Telegram, email и т.п.).
	•	Хранилище долгосрочной памяти (NeonTech: Supabase/Postgres + Qdrant) – Backend/Data-инженеры:
	•	Проектирование и разворачивание базы знаний для долгой памяти ассистента. Решение между Supabase (Postgres) с векторным расширением или отдельной векторной БД Qdrant – выбор на основе требований (масштаб, скорость, удобство).
	•	Настройка хранения эмбеддингов: определение схемы таблиц или коллекций (например, таблица LongMemory с полями: embedding (vector), text, метаданные (пользователь, источник, метки), timestamp).
	•	Реализация сервисов добавления новой информации в долгосрочную память: сохранение важных данных из диалогов (например, выводы, новые факты), векторизация их через Jina Embedding и сохранение в БД. Минимизировать хранение сырых больших текстов – по возможности хранить сжатые представления или ссылки.
	•	Реализация поиска по векторному хранилищу: метод для поиска ближайших эмбеддингов (semantic search) по запросу пользователя. Это может быть REST API endpoint в Laravel, вызываемый либо напрямую фронтендом (редко), либо самим LLM как инструмент (чаще), либо Laravel перед отправкой запроса в LLM.
	•	Обеспечение быстрого доступа: индексирование эмбеддингов, периодическая оптимизация (если Qdrant – настройка shards, if Postgres – поддержка pgvector).
	•	Безопасность и изоляция данных: если память персонализирована, гарантировать, что эмбеддинги пользователей изолированы друг от друга (например, с помощью user_id в метаданных запросов).
	•	Политика хранения: минимизация объема данных – команда продумывает TTL или архивацию данных. Например, сохранять только сведения, которые будут нужны для будущих запросов (сжатые конспекты диалогов, важные факты). Менее актуальные векторы могут удаляться или выгружаться в холодное хранилище.
	•	Хранилище краткосрочной памяти (Upstash Redis) – Backend/DevOps:
	•	Настройка облачного Redis (сервис Upstash) для хранения состояния диалога и других временных данных с низкой задержкой.
	•	Определение структуры данных Redis для короткой памяти: например, храним последние N сообщений диалога пользователя, идентификаторы инструментов, временные токены, и пр. Используем ключи по идентификатору сессии или пользователя (например, session:{user_id}:recent_messages).
	•	Внедрение TTL (Time-to-Live) для записей короткой памяти: сообщения хранятся ограниченное время (например, несколько часов или дней) чтобы не накапливать избыточно данные. Это соответствует принципу “работать от запроса пользователя” – при каждом новом запросе брать актуальный контекст, но не хранить навсегда все диалоги.
	•	Обеспечение доступности: Upstash – serverless Redis, поэтому настроить количества подключений, персистенцию (если нужна для сессий) и гарантировать, что задержка минимальна (близость к серверу Laravel/RunPod по региону).
	•	Реализация механизмов очистки/обновления: например, после получения ответа можно обновить краткосрочную память (добавить новое сообщение, удалить самое старое если превышен лимит). Команда бэкенда прописывает эти операции в коде логики чата.
	•	Мониторинг использования памяти: настройка алертов или дэшбордов (возможно через Upstash мониторинг) чтобы следить за объемом хранимых данных и скоростью запросов.
	•	Интерфейс диалога LLM (AG-UI) – Frontend/UI/UX:
	•	Оценка целесообразности использования AG-UI: команда UI/UX проводит исследование возможностей AG-UI — поддерживает ли он необходимый функционал (подсветка шагов размышления LLM, визуализация источников, редактирование сообщений, мульти-диалоги и т.д.).
	•	Интеграция или разработка UI: если принято решение использовать AG-UI, интегрировать его в SvelteKit приложение или как отдельное веб-приложение, связанное с основным API. Обеспечить совместимость стилей и логики (возможно, потребуется адаптация AG-UI под наш стек).
	•	Если AG-UI окажется нецелесообразным, продолжить развитие собственного интерфейса: предусмотреть все нужные элементы UI (список диалогов, окно чата, уведомления о действиях, индикаторы активности бота).
	•	Ответственные: назначить ответственного за этот компонент (вопрос, пока “пока никто не отвечает” – найти владельца). Вероятно, фронтенд-разработчик с уклоном в дизайн или отдельный UX-специалист.
	•	Связь с ядром: убедиться, что UI корректно отображает взаимодействие с LLM – например, если LLM выполняет инструменты (web search, parsing), возможно, показывать пользователю промежуточные шаги (по желанию), либо хотя бы индикатор прогресса.
	•	Мониторинг и логирование LLM (Langfuse) – DevOps/Data/ML:
	•	Внедрение системы мониторинга: подготовить интеграцию с Langfuse для сбора телеметрии по запросам к LLM. Langfuse позволит отслеживать последовательность prompt→ответ, вызовы инструментов, время выполнения каждого шага, возможные ошибки или сбои.
	•	Ответственные: назначить инженера (DevOps или ML), ответственного за мониторинг. На текущий момент “никто не отвечает” за Langfuse – необходимо определить владельца этого направления.
	•	Техническая интеграция: добавить в код взаимодействия с LLM хуки отправки данных в Langfuse. Например, после каждого пользовательского запроса логировать: ID запроса, текст запроса (в обезличенном виде), использованные инструменты, время ответа, длину ответа, токенизацию и пр.
	•	Настройка дэшбордов и алертов: определить KPI (например, среднее время ответа, процент неудачных вызовов инструментов, расход токенов) и настроить в Langfuse панели для команды. При отклонениях (замедление, ошибки) – уведомления соответствующим разработчикам.
	•	Безопасность и конфиденциальность: убедиться, что в логи не попадают чувствительные данные пользователя (или они хранятся обезличенно/хэшировано). Langfuse должен соответствовать требованиям GDPR/политики безопасности, если хранятся пользовательские запросы.
	•	Периодический анализ логов: проводить ревью собранных данных, чтобы улучшать систему (например, видеть, какие инструменты вызываются чаще всего и оптимизировать их, где модель дает сбои – улучшить prompt или логику).
	•	Интеграция клиентов: Telegram и WhatsApp – Backend/DevOps/Integration:
	•	Подготовка аккаунтов/ботов: зарегистрировать и настроить Telegram Bot и подключение к WhatsApp Business API (или через провайдера типа Twilio, если используется). Учитывать, что рассылка платных уведомлений через эти каналы должна соответствовать политикам платформ.
	•	Реализация шлюза в Laravel для этих клиентов: настроить вебхуки (Webhook) или периодический пуллинг для получения сообщений от Telegram/WhatsApp. Например, маршрут /webhook/telegram обрабатывается Laravel и трансформирует входящее сообщение в формат, понятный основной системе (например, как обычный пользовательский запрос).
	•	Авторизация и сопоставление: привязать учетные записи мессенджеров к нашим пользователям. Например, при первом обращении через Telegram – запросить идентификатор пользователя нашей системы или использовать телефон/email для мэппинга. Продумать безопасность, чтобы чужой Telegram не смог получить чужие данные.
	•	Отправка ответов и уведомлений: из Laravel вызывать API Telegram/WhatsApp для доставки ответа ассистента пользователю. Убедиться, что форматирование ответа подходит для мессенджера (текст, возможно, markdown/HTML ограничения, эмодзи).
	•	Учесть ограничения: у Telegram есть ограничение на длину сообщений и скорость отправки, у WhatsApp – требования шаблонов для уведомлений. Команда интеграции должна соблюдать эти нюансы (например, длинные ответы разбивать, либо отправлять как файл, если нужно).
	•	Зона ответственности: поддержка этих интеграций – обновление токенов API, отслеживание изменений в API мессенджеров, обработка ошибок доставки. Вероятно, этим занимается backend-команда, но возможно выделить отдельного инженера, т.к. каналы критичны для платных клиентов.

Архитектура системы (дерево компонентов)

Ниже представлена иерархия компонентов системы и их взаимодействие в архитектуре:
	•	Клиентские приложения (точки входа пользователей):
	•	Web-клиент (SvelteKit SPA) – основное приложение, через которое пользователи взаимодействуют с ассистентом. Выполняет запросы к бэкенду, отображает диалог и результаты.
	•	Мессенджер Telegram (Bot) – сторонний клиент, где пользователь отправляет сообщения боту, которые перенаправляются в нашу систему.
	•	Мессенджер WhatsApp (Business API) – аналогично Telegram: пользователь общается с ботом/ассистентом через интерфейс WhatsApp.
	•	Backend-сервер (Laravel Cloud):
	•	API шлюз – принимает запросы от веб-клиента (HTTP POST запросы чата, WebSocket сообщения) и вебхуки от мессенджеров. Валидирует входящие данные, управляет сессиями.
	•	Контроллер диалога – основная логика обработки запроса пользователя: формирование контекста, обращение к LLM, получение ответа, отправка ответа обратно клиенту.
	•	Интерфейс к памяти – подкомпонент, отвечающий за взаимодействие с БД памяти: быстрый доступ к Redis (краткосрочная память), запросы к векторному хранилищу (долгосрочная память) при подготовке контекста.
	•	Инструменты (API для LLM) – набор эндпоинтов, которые могут вызываться моделью как внешние инструменты:
	•	Парсинг веб-страниц: эндпоинт, принимающий URL, запускающий Puppeteer/другой сервис и возвращающий распаршенные данные (текст, JSON структурированные данные).
	•	Поиск/вопрос к базе знаний: эндпоинт для запросов к долгосрочной памяти (по эмбеддингам) – возвращает найденные фрагменты знаний.
	•	(Другие инструменты): при необходимости, например, калькулятор, доступ к внешним API (погода, новости), которые модель сама точно не знает.
	•	Сервис уведомлений – модуль отправки исходящих сообщений/уведомлений через внешние сервисы (Telegram, WhatsApp, email). Получает от контроллера диалога контент, выбирает канал и отправляет.
	•	Логирование и мониторинг – интеграция с Langfuse: сбор информации о запросах, результатах, проблемах и отправка их на сервер мониторинга. А также классическое логирование Laravel (на случай отладки).
	•	Платформа искусственного интеллекта (хостится на RunPod или аналог):
	•	LLM-модель (LLaMA3) – ядро AI, генерирующее ответы. Загружена на GPU, доступна через API или напрямую вызывается контроллером Laravel.
	•	Модуль Tool-calling (Агент) – прослойка, обеспечивающая модели возможность прерывать генерацию и запрашивать внешние данные. Содержит описание доступных инструментов (сигнатуры функций, например parse_url(url) или search_memory(query)) и логику, как модель их вызывает (через HTTP запросы к бэкенду).
	•	Jina Embeddings & Vector Search – компонент для работы с эмбеддингами. В некоторых вариантах реализуется прямо на AI-платформе: модель или вспомогательный скрипт генерирует embedding для запроса пользователя и может выполнить векторный поиск, если есть локальная копия базы. Однако в нашей архитектуре основное хранилище векторной памяти – внешнее (Neon/Qdrant), поэтому этот компонент скорее выносится на бек. Здесь же может находиться клиент для обращения к Qdrant или Supabase (через HTTP/Python SDK) если решим искать напрямую из ML-сервиса.
	•	Инструменты внутри AI – реализация некоторых утилит локально:
	•	Вызов Puppeteer/Browser: при запросе parse_url можно инициировать Node.js Puppeteer (в контейнере RunPod) или вызывать удаленно. Если Puppeteer развёрнут рядом с моделью, AI-платформа через Tornado выполняет асинхронно получение страницы и выдает результат модели.
	•	BeautifulSoup: парсинг HTML может выполняться Python-скриптом после получения HTML через Puppeteer или обычный HTTP GET (для статичных страниц).
	•	OpenEvolve: модуль, выполняющий оптимизацию/эволюцию кода или решений, может быть вызван моделью для специфических сценариев (например, когда задача – сгенерировать и улучшить код). В архитектуре это опциональный компонент, который взаимодействует с моделью по запросу.
	•	API слой (Tornado Web Server) – обеспечивает HTTP-интерфейс к модели (если модель не встроена прямо в Laravel). Laravel при вызове LLM обращается к этому API (например, посылает JSON с prompt и параметрами, получает поток или полный ответ). Tornado также может обрабатывать параллельно поступающие запросы и обеспечивает необходимую скорость обмена.
	•	Система памяти:
	•	Краткосрочная память (Upstash Redis) – внешнее быстрое хранилище (Redis в облаке) для хранения текущего состояния диалога и недавних данных. Laravel читает/пишет в него недавние сообщения перед отправкой запроса в LLM и после получения ответа. LLM напрямую сюда не пишет (только через Laravel).
	•	Долгосрочная память (Neon/Supabase + Qdrant) – база данных знаний и истории:
	•	Постгрес (Supabase/Neon) хранит данные диалогов или документов, векторный индекс (pgvector) или отдельно Qdrant хранит эмбеддинги для семантического поиска.
	•	Laravel или ML-сервис добавляет новые записи сюда по мере возникновения нового важного контекста (например, сохранение summary долгой беседы, новых фактов от пользователя).
	•	По запросу (через инструмент или заранее) происходит поиск ближайших эмбеддингов для актуального вопроса, и найденный контент возвращается модели как часть контекста.
	•	Принцип минимального хранения: вместо сырого текста хранятся или ссылки на данные, или сжатые конспекты. Обновление информации по мере устаревания (чтобы база не разрасталась бесконтрольно).
	•	Интерфейс диалогов (AG-UI):
	•	Если будет внедрен, он может быть либо:
	•	Встроен во фронтенд SvelteKit (в виде компонента или CSS-стиля + логики),
	•	Либо как отдельное приложение, связанное с нашим backend по API.
	•	Он служит прослойкой между пользователем и нашим SvelteKit, предоставляя улучшенный UX для общения с LLM.
	•	В иерархии компонентов это необязательный слой: если не используется, SvelteKit UI напрямую общается с Laravel; если используется, SvelteKit может обернуть AG-UI или переиспользовать его компоненты.
	•	Мониторинг (Langfuse):
	•	Не участвует напрямую в потоке данных для ответа, но на уровне архитектуры внедрён во все критичные точки:
	•	Backend Laravel: логирует события запроса/ответа (метаданные: user_id, время, и др.).
	•	ML-сервис: отправляет телеметрию по работе модели (например, usage токенов, какие инструменты вызывались).
	•	Langfuse работает как отдельно стоящий сервис, которому наши компоненты передают данные. Коммуникация обычно асинхронная (чтобы не тормозить ответ пользователю).

Диаграмма взаимодействий в целом будет выглядеть так: пользовательское приложение отправляет запрос в Laravel API, который обогащает его контекстом из краткой/долгой памяти, затем перенаправляет запрос к LLM-сервису. LLM при необходимости запрашивает дополнительные данные через инструменты (возвращаясь к Laravel API для парсинга или поиска), после чего генерирует окончательный ответ. Этот ответ через Laravel передается обратно клиенту. Все ключевые события фиксируются в Langfuse для мониторинга. Дополнительные клиенты (Telegram/WhatsApp) вписываются в эту схему, взаимодействуя с Laravel на входе и выходе, минуя веб-frontend.

Обработка запросов: память и парсинг

Чтобы минимизировать постоянное хранение данных и работать “от запроса пользователя”, система обрабатывает каждый запрос динамически, используя хранилища памяти только при необходимости. Ниже описан шаг за шагом процесс обработки пользовательского запроса с учетом выборочного обращения к памяти и инструментам парсинга:
	1.	Получение запроса: Пользователь отправляет сообщение ассистенту (через веб-UI или мессенджер). Laravel Backend получает этот запрос (через REST API или webhook) вместе с контекстной информацией (например, идентификатор пользователя или сессии).
	2.	Извлечение короткой памяти: Контроллер диалога Laravel обращается к Upstash Redis с целью получить недавнюю историю диалога для данного пользователя/сессии. Например, подтягиваются последние N реплик пользователя и ассистента (если они есть). Это обеспечивает локальный контекст, чтобы LLM помнил, о чём была речь в недавней беседе, без хранения всей истории на диск.
	3.	Поиск в долгосрочной памяти (при необходимости): Если текущий запрос пользователя предполагает обращение к ранее известной информации (например, пользователь задаёт вопрос о факте, упомянутом несколько диалогов назад, или по теме, которая явно хранится в базе знаний), бэкенд выполняет следующие шаги:
	•	Генерирует embedding запроса пользователя. Этот embedding может быть получен с помощью Jina Embedding или аналогичной модели (вызов происходит либо в Laravel через Python-скрипт, либо на AI-платформе).
	•	С помощью полученного embedding делает семантический поиск по векторной базе (Neon/Qdrant). Запрос: найти самые релевантные куски информации, связанные с текущим вопросом. Например, это могут быть фрагменты предыдущих диалогов или документов, которые пользователь загружал ранее.
	•	Получает набор результатов (тексты + метаданные) с оценкой близости. Отфильтровывает нерелевантные.
	•	Подготовка контекста: формирует структурированный контекст для LLM. Например, добавляет в prompt блоки: “Вот важная информация из прошлых взаимодействий:” и перечисляет 2-3 самых подходящих фрагмента из долгосрочной памяти. (Примечание: если поиск не дал результатов выше определённого порога похожести – значит, долгосрочную память можно не привлекать для данного запроса.)
	•	Все эти данные извлекаются динамически по запросу, ничего лишнего постоянно не хранится или не загружается.
	4.	Формирование запроса к модели: Laravel объединяет данные:
	•	Формирует промпт/запрос для LLM, включающий: сообщение пользователя, недавнюю историю (из Redis) и вставленный контекст из долгосрочной памяти (если был найден на шаге 3). Также могут быть включены системные инструкции (например, стиль ответа, ограничения).
	•	Отправляет этот скомпонованный запрос на AI-платформу (через HTTP вызов к Tornado-серверу, либо иным RPC).
	5.	Обработка моделью LLaMA3:
	•	Модель получает на вход сформированный промпт с контекстом и начинает генерировать ответ.
	•	Вызов инструментов (tool calling): если в процессе генерации ответа модель приходит к тому, что ей нужны дополнительные данные (например, “нужно получить свежую информацию с веб-сайта” или “нужно выполнить вычисление/парсинг”), она формирует специальный «запрос инструмента». Этот запрос может быть реализован, например, в формате JSON или оговорённой строке, которую Tornado/агент распознает.
	•	Tornado (или другой управляющий код) перехватывает этот запрос инструмента и выполняет соответствующее действие:
	•	Парсинг веб-страницы: если модель запросила parse_url("http://..."), сервер вызывает модуль парсинга. Вариант 1: передать задачу парсинга обратно Laravel (на спец. эндпоинт), где Puppeteer/Chrome безголовый загрузит страницу, затем BeautifulSoup извлечёт текст. Вариант 2: выполнить парсинг внутри среды RunPod (например, запустив pyppeteer или HTTP-запрос и используя BeautifulSoup). Выбор варианта – по соображениям эффективности и удобства разработки (в рамках гибкого разделения логики, см. рекомендации ниже). После получения результата (текст страницы или нужные данные) Tornado возвращает их модели.
	•	Обращение к памяти как инструмент: модель может явно вызвать, например, search_memory("ключевой факт") (если мы предоставим ей такую возможность). Тогда Tornado или Laravel выполнит поиск по векторной базе (аналогично шагу 3) и вернёт результаты модели. (Однако чаще поиск по памяти мы делаем на шаге 3 проактивно, чтобы модель сама не тратила токены на принятие решения об этом. Инструмент “memory” может быть резервным, если что-то упущено.)
	•	Другие инструменты: модель может иметь доступ к утилитам (например, вычисление выражения, вызов внешнего API). Каждый такой инструмент – это либо функция, реализованная на Tornado-сервере, либо HTTP-эндпоинт в Laravel. Торнадо распознаёт команду и перенаправляет на нужную функцию/эндпоинт, результат возвращает модели.
	•	Продолжение генерации: получив данные от инструмента, модель продолжает формировать ответ, используя новую информацию. Модель может поэтапно вызвать несколько инструментов, если нужно (например, сначала получить страницу, потом задать уточняющий вопрос по её содержимому). Вся эта цепочка происходит внутри AI-платформы, а пользователь ждёт конечного ответа.
	6.	Возврат ответа: LLM завершает генерацию ответа на вопрос пользователя, учитывая весь предоставленный контекст и данные от инструментов. Полученный ответ отправляется обратно в Laravel (через Tornado API ответ).
	7.	Пост-обработка и доставка: Laravel получает ответ от модели. Далее:
	•	Опционально, бэкенд может чуть отформатировать ответ (например, обернуть ссылки в markdown, добавить разметку для лучшего отображения в UI). Минимальная модификация, чтобы не исказить смысл, в основном – для удобства клиента.
	•	Запись новой информации в память: бэкенд может извлечь из ответа или из данных процесса что-то, что стоит сохранить. Например, если модель узнала новый факт от пользователя или снаружи – можно сохранить его в долгосрочной памяти (через embedding в векторную БД). Либо сохранить summary текущего диалога, если он был длинным, чтобы использовать в будущем вместо сырых реплик. Эти действия выполняются асинхронно, чтобы не задерживать пользователя: например, с помощью очереди Laravel или фонового задания.
	•	Обновление краткосрочной памяти: Redis обновляется – добавляется очередное сообщение пользователя и ответ ассистента, старые сообщения удаляются если превышен лимит. Таким образом, при следующем запросе недавний контекст будет доступен, а дальний – постепенно уходит (и, возможно, сохранён как summary в долгой памяти).
	•	Логирование в Langfuse: отправка записи о запросе и ответе, времени выполнения, использовании инструментов. Это тоже может быть асинхронно или параллельно.
	•	Формирование и отправка ответа клиенту: бэкенд отправляет ответ пользователю. Для веб-клиента – JSON по HTTP или через WebSocket (который фронт отобразит в чате). Для Telegram/WhatsApp – вызов API соответствующего, чтобы пользователь получил сообщение в мессенджере.
	8.	Очистка и минимизация хранения: Завершив обработку, система оставляет в постоянном хранилище только необходимое:
	•	В Redis остаётся только небольшое окно недавних сообщений.
	•	Полная сырая история не сохраняется в базу (если нет особой надобности) – вместо этого может сохраняться короткое резюме длинного диалога или ключевые факты.
	•	Векторная база обновляется только важными знаниями, чтобы в будущем ассистент мог к ним обращаться.
	•	Логи в Langfuse хранят техническую информацию для мониторинга, но могут быть обезличены или периодически очищаться согласно политикам хранения.

Таким образом, каждый запрос обрабатывается «с нуля» с подтягиванием нужного контекста on-demand. Это обеспечивает невысокие постоянные требования к хранению данных и масштабируемость: добавление новых пользователей не приводит к экспоненциальному росту хранимых диалогов, т.к. система хранит лишь агрегированную информацию по мере необходимости.

Распределение логики между Laravel и LLaMA3

В проекте некоторые функции могут быть реализованы либо на стороне классического бэкенда (Laravel), либо в самом LLM через механизмы tool calling. Важно грамотно и гибко разграничить ответственность, чтобы использовать сильные стороны каждой стороны. Ниже приведены рекомендации по распределению логики:
	•	Backend (Laravel) – “Источник правды” и критичные операции:
Laravel должен отвечать за всю бизнес-логику, требующую надежности, контроля и интеграции с внешними системами. Сюда относятся:
	•	Аутентификация, права доступа, платежи: всё, что связано с учетными записями, проверками подписки, тарификацией, должно быть только на Laravel. LLM не должен принимать решения, кому отвечать – это делает бекенд.
	•	Вызовы внешних API и систем, где важна точность и проверка: например, запрос к базе данных пользователя, проведение транзакции, отправка email. Laravel обеспечивает, что эти операции выполнены правильно, и возвращает результат LLM при необходимости.
	•	Инструменты, требующие долгого выполнения или сложного стека: парсинг веб-страниц, сложные вычисления, доступ к корпоративным системам. Их надежнее делать на бэкенде, где можно обработать ошибки, повторить попытку, логировать отдельно.
	•	Предобработка и постобработка данных: Laravel может брать на себя очистку пользовательского ввода (sanitize), а также форматирование ответа (например, разбить на сообщения, добавить заголовки). Это структурные задачи, которые не должны расходовать контекст LLM.
	•	Управление состоянием: хранение и выборка памяти, обновление баз – все это делает бэкенд по алгоритмам, которые мы задали. Модель лишь запрашивает “дай мне X”, а Laravel решает, как именно получить X.
	•	LLM (LLaMA3) – “Мозг” для нечетких задач и обработки языка:
Модель используется там, где нужна семантическая обработка, генерация текста, извлечение смысла. Ее сила – в понимании контекста и гибкости, поэтому поручаем:
	•	Формирование ответов на вопросы пользователей: основная задача LLM – анализировать пользовательский запрос и контекст, генерировать осмысленный ответ на естественном языке. Это то, что вручную в коде не запрограммируешь – творчество, обобщение, выводы.
	•	Решение, какие инструменты задействовать (в пределах предоставленного набора): модель сама может в процессе решить, что ей, например, не хватает информации, и она должна сделать веб-поиск или вызвать калькулятор. Эти решения основаны на контексте вопроса. Мы предоставляем модели возможность и описания инструментов, но не навязываем когда именно вызывать – это гибкость со стороны LLM.
	•	Семантический поиск в памяти: альтернативный подход – прямо внутри модели спросить: “найди в памяти факт о X”. Можно передать модели резюме памяти, но иногда эффективнее, чтобы модель сформировала эмбеддинг и сама вызвала поиск. Однако, генерацию эмбеддинга мы обычно делаем вне модели (модель может выдавать vector в hidden state, но это сложно), поэтому компромисс: модель говорит, что искать, а Laravel выполняет поиск (как инструмент).
	•	Обработка неструктурированных данных: если, к примеру, инструмент парсинга вернул HTML или сырой текст, LLM может взять на себя извлечение нужной информации, резюмирование текста, переводы. Т.е. Laravel достает сырье, а модель “превращает в золото” – делает содержание понятным, отвечает на вопрос пользователя на основе него.
	•	Гибкая логика диалога: ведение контекстуальной беседы, изменение стиля ответа по просьбе пользователя, выяснение уточнений – всем этим управляет модель по ходу диалога, а не жестко заданные правила кода.
	•	Гибкое разделение и расширяемость:
	•	Проектируя инструменты, следует держать интерфейсы максимально универсальными. Например, сделать обобщенный эндпоинт /api/tool/{tool_name} на Laravel, куда модель может послать запрос с параметрами. Laravel проверит tool_name и выполнит соответствующую функцию. Так мы можем добавлять новые инструменты без изменения логики модели – просто описав новой версии LLM, что появился еще такой функционал.
	•	Дублирование важных функций: На случай сбоя LLM, критичные функции должны быть продублированы на бэкенде. Например, если модель почему-то не вызвала поиск по базе знаний, Laravel может сам иногда делать превентивно (как на шаге 3 обработки запроса). Или если модель не сумела разобрать результат парсинга, Laravel может подстраховать (хотя бы проверить, не пустой ли ответ).
	•	Минимизировать зависимости: Логику, не требующую понимания языка, лучше выносить из LLM. Например, парсинг HTML – модель не должна читать весь HTML, ей лучше дать уже очищенный текст. Значит, инструмент “parse_url” должен возвращать именно текст/данные, а не raw HTML. Это разгружает модель.
	•	Безопасность: доверять LLM можно не во всем. Она не должна напрямую выполнять произвольный код или бесконтрольно вызывать внешние API без проверки. Поэтому Laravel служит прослойкой: получив от модели команду инструмента, проверяет, что запрос допустим (например, URL в белом списке, или команда разрешена) и только потом выполняет. Такой sandbox для AI.
	•	Эволюция логики: со временем некоторые решения могут мигрировать между уровнями. Например, если увидим, что модель часто совершает определенную ошибку, можно перенести эту часть на backend (жестко запрограммировать проверку). Или наоборот, если какая-то часть логики стала хорошо поддерживаться моделями (например, новая версия LLM умеет делать что-то встроенно), можно упростить backend.

В целом, Laravel отвечает за контролируемое выполнение и хранение, LLM – за интеллектуальное содержимое. Правильное сочетание: модель генерирует и решает, когда ей нужны данные, а Laravel предоставляет эти данные и обеспечивает рамки (state management, external operations).

Очередность задач (пошаговый план реализации)

При построении системы рекомендуется этапный подход. Ниже представлен примерный порядок внедрения компонентов и функционала, с указанием приоритетов и ответственных:
	1.	Базовая инфраструктура и окружение – DevOps, Backend, ML:
	•	Развернуть среду для Backend Laravel (например, Laravel Forge или облачный Kubernetes/VM). Настроить базовый проект, подключение к БД (Postgres/Supabase для пользователей, если нужно).
	•	Настроить RunPod (или иной сервер) с доступом к GPU, развернуть окружение с необходимыми зависимостями: Python 3, библиотеки для LLaMA3, Tornado, Jina, Puppeteer (Nodejs), BeautifulSoup, etc.
	•	Развернуть Redis (Upstash) и векторную БД (если сразу используем Qdrant или Supabase) – создать инстансы, проверить соединение. Поскольку хранение данных минимально, на первых порах хватит тестовых экземпляров.
	2.	Основной backend и frontend (скелет) – Backend & Frontend команды:
	•	Backend: Реализовать базовые маршруты Laravel: health-check, аутентификация (если нужна сессия пользователя), простой эндпоинт отправки сообщения от пользователя. Пока можно заглушкой возвращать фиксированный ответ, чтобы протестировать цепочку.
	•	Frontend: Создать структуру SvelteKit-приложения, настроить маршруты, подключить TanStack Query. Реализовать простую страницу с чат-интерфейсом (инпут для вопроса, область для вывода ответа). Пока ответ – от заглушки бэкенда.
	•	Связь фронт-бек: настроить вызов API Laravel из SvelteKit через TanStack Query (или fetch) при отправке сообщения. Убедиться, что запрос уходит и ответ (пускай статичный) отображается.
	3.	Интеграция LLM (первичная) – ML & Backend:
	•	Поднять на RunPod сервис с моделью LLaMA3. Для начала можно без сложных tool-вызывов – просто endpoint, который принимает prompt и возвращает сгенерированный ответ.
	•	На Laravel настроить клиента для обращения к LLM-сервису (HTTP запрос или gRPC, в зависимости от реализации). Связать эндпоинт чата с реальной моделью: принимать вопрос пользователя, отправлять на LLM, получать и возвращать ответ.
	•	Покрыть базовый сценарий: пользователь задает вопрос -> LLM отвечает (без памяти и инструментов пока). Убедиться, чтоLatency и базовая работа модели в порядке.
	4.	Краткосрочная память (контекст диалога) – Backend:
	•	Реализовать в Laravel подключение к Upstash Redis. Настроить хранение последних N сообщений диалога: добавить в логику контроллера чата сохранение вопрос-ответ в Redis с привязкой к пользователю/сессии.
	•	Реализовать извлечение последних сообщений при новом запросе и включение их в prompt для LLM (например, в виде: “User: …, Assistant: …” пар нескольких последних пар).
	•	Покрыть случай продолжения беседы: спросить у ассистента что-то, потом второй вопрос, убедиться, что во втором запросе ему передаются предыдущие сообщения и модель учитывает контекст.
	5.	Долгосрочная память (база знаний) – Backend/Data:
	•	Определиться с решением (Supabase pgvector или Qdrant). Допустим, начать с Qdrant для быстрого старта. Развернуть Qdrant (если не сделано) или настроить Supabase с расширением pgvector.
	•	Интегрировать библиотеку Jina Embedding или аналог для получения эмбеддингов на Laravel или ML-сервисе. Например, может быть Python-скрипт, который вызывается Laravel через CLI (или прямой вызов через Python выполняется).
	•	Реализовать функцию добавления знаний: написать метод, который берёт текст + метаданные -> получает embedding -> сохраняет в Qdrant/БД. Попробовать добавить вручную пару тестовых записей (факт о пользователе, часть документа) и проверить, что они сохраняются.
	•	Реализовать поиск по памяти: метод, принимающий запрос (строку) -> вычисляет embedding -> ищет векторно в базе -> возвращает top-N результатов с косинусным расстоянием. Сделать Laravel-эндпоинт /api/tool/memory_search для этого (или встроить в контроллер).
	•	Включить поиск памяти в общий поток: добавить логику в контроллер чата перед вызовом LLM – если определён флаг/условие (например, всегда пробуем, либо если история пуста, либо если пользователь запросил что-то связанное с прошлым), то вызвать memory_search и включить результаты в prompt.
	•	Протестировать сценарий: сохранить в память факт (например: “Компания основана в 2020”), затем спросить ассистента “Когда основана компания?”. Проверить, что без сохранения он не знал, а с сохранением – может извлечь ответ из переданного контекста.
	6.	Tool calling (инструменты для LLM) – ML & Backend:
	•	На стороне AI-платформы подготовить механизм, позволяющий модели вызывать функции. Например, определить формат сообщений типа: модель генерирует специальный токен или строку ([TOOL_CALL]{ "name": "parse_url", "args": ["http://example.com"] }) – и реализовать в Tornado разбор этого. Это может потребовать донастройки модели (в промпте описать, как вызывать функции, или fine-tune, либо использовать возможности LLM, если поддерживает plugin/tool use).
	•	Парсинг веб-страниц: Реализовать инструмент parse_url:
	•	Backend: создать эндпоинт /api/tool/parse_url (или интегрировать в существующий контроллер инструментов). При вызове – запускает Puppeteer (через Node сервис или Puppeteer Sharp, или Playwright) чтобы получить контент страницы. Затем очищает его (например, достает видимый текст, может ограничить по длине) и возвращает JSON или текст.
	•	ML: в описании инструментов указать модели, что parse_url(url) возвращает содержимое страницы по ссылке.
	•	Связать: Tornado при получении команды parse_url вызывает этот эндпоинт Laravel, получает данные и передает обратно модели.
	•	Другие инструменты: по приоритету добавить, например, calculator(expression) – простой парсер математических выражений в Laravel, search_memory(query) – (хотя у нас уже есть memory_search как часть backend-логики; можно позволить модели явно запрашивать дополнительный поиск). Если есть потребность – web_search(query) (инструмент, который делает HTTP-запрос к поисковому API, если нужен внешний интернет-поиск).
	•	Протестировать tool calling end-to-end: попросить пользователя задать вопрос, требующий инструментов (например: “Сколько фотографий на главной странице example.com?” – модель должна вызвать parse_url->получить HTML->посчитать). Проверить, что цепочка выполняется и ответ возвращается.
	7.	Расширение frontend (UI) и UX-функциональности – Frontend/UI:
	•	Добавить в интерфейс индикацию процесса: когда пользователь задал вопрос, показать “Ассистент думает…” или анимацию. Если мы можем стримить ответ, отобразить его постепенно.
	•	Оформить вывод ответов красиво: разбить на абзацы, поддержать markdown (если LLM возвращает форматированный текст), ссылки кликабельные.
	•	Если инструмент парсинга возвращает большие тексты, подумать о способе отображения (может, ассистент будет давать сокращенную информацию).
	•	AG-UI: параллельно провести оценку/прототип. Например, взять компонент AG-UI и попробовать встроить: сравнить, не дублирует ли он то, что уже сделано. Если AG-UI дает качественный скачок (например, удобный список диалогов, или готовый стиль чата), решить о его внедрении. Внедрение: либо заменить текущие компоненты на AG-UI, либо перенять идеи/код.
	•	Начать поддерживать многоканальность: предусмотреть в веб-интерфейсе, что пользователь может подключить свой Telegram/WhatsApp для уведомлений. Например, дать ссылку “Добавить бота в Телеграм” или QR-код для WhatsApp, после чего подтверждать связь аккаунтов.
	8.	Интеграция Telegram и WhatsApp – Backend/Integration:
	•	Реально настроить Telegram-бота: получить токен, установить вебхук на Laravel (этап 1 готовил инфраструктуру, теперь код). Реализовать контроллер, обрабатывающий сообщения: трансформировать их в запрос к общему сервису (по сути, вызывать тот же метод, что и веб-клиент).
	•	Адаптировать логику ответа: для Telegram, возможно, ответы >4096 символов надо делить. Для WhatsApp использовать шаблоны/форматирование поддерживаемое (текст, emoji).
	•	Добавить в Laravel обработку команд/стартовых сообщений (например, /start в Telegram, подписка/отписка на уведомления).
	•	Тестирование: пройти полный сценарий – пользователь пишет боту, запрос идет в систему, LLM отвечает, ответ возвращается в чат. Исправить возникающие баги (например, ручка payload JSON vs form-data, проблемы кодировки).
	•	Обеспечить, чтобы платные уведомления отправлялись: например, настроить Laravel command, который по событию (готов ответ, или по расписанию) шлет сообщение пользователю, оплатившему услугу, через WhatsApp.
	9.	Внедрение мониторинга (Langfuse) – DevOps/ML:
	•	Подключить SDK или API Langfuse на бэкенде и AI-платформе. В Laravel – в местах получения запроса и отправки ответа, а также внутри инструментов (при ошибках) вызывать отправку событий в Langfuse (например, Langfuse.log(event) с нужными параметрами). В ML-сервисе – вокруг вызовов модели и инструментов.
	•	Протестировать сбор данных: убедиться, что каждый запрос логируется (можно в тестовом режиме), видны последовательности. Настроить минимальный дэшборд.
	•	Постепенно расширять охват: логировать использование памяти (сколько результатов из памяти вытащили, длину контекста), время работы Puppeteer, и др.
	•	Организовать регулярный просмотр метрик командой: например, раз в неделю проверять Langfuse-отчеты, чтобы обнаруживать узкие места или рост нагрузки.
	10.	Оптимизации и отладка – Все команды:
	•	Провести интеграционное тестирование всего потока: разные сценарии (простой вопрос, вопрос требующий памяти, требующий парсинга веба, длительный диалог, одновременные запросы от нескольких пользователей). Найти узкие места:
	•	Оптимизировать скорость: при необходимости кешировать результаты часто используемых инструментов (например, если многие спрашивают одно и то же – можно хранить в Redis результаты некоторого парсинга на короткое время).
	•	Балансировка нагрузки: настроить авто-масштабирование RunPod instance или очередь запросов, если много одновременных обращений к LLM.
	•	Оптимизировать стоимость: следить за объемом хранимых данных (очищать старое), за использованием токенов (может, уменьшить окно памяти, или длину контекста где можно).
	•	Улучшить разделение логики на основе практики: возможно, перенести некоторые решения “в модель” или наоборот “в код” по опыту первых пользователей. Например, если видим, что модель стабильно справляется с веб-поиском, можно позволить ей больше решать самой когда его вызывать. Или если она часто делает лишние вызовы, ограничить через backend.
	•	Закрепить зоны ответственности: к этому шагу станет ясно, какая команда какие компоненты постоянно поддерживает. Обновить документацию архитектуры, чтобы новые участники команды понимали структуру.
	11.	Оценка AG-UI (финальное решение) – Frontend/UI:
	•	Принять окончательное решение по AG-UI на основе прототипа и отзывов. Если решено внедрять полностью – планировать миграцию интерфейса на него, с учетом поддержки всех функций (память, многоканальность, и т.д.). Если нет – удалить экспериментальный код, сосредоточиться на своем UI, возможно, вдохновившись лучшими идеями из AG-UI.
	•	В обоих случаях, документировать решение и причины, чтобы все заинтересованные знали, как двигаемся дальше с UI.
	12.	Релиз и дальнейшее развитие:
	•	После того, как все основные компоненты работают вместе, подготовить проект к публичному релизу: написать техническую документацию, обучить команды поддержки.
	•	Составить план дальнейшего развития: новые инструменты для LLM (например, интеграция с внутренними базами данных клиента, если потребуется), обновление модели LLaMA3 до более новой версии или fine-tuning под специфику диалогов, расширение поддерживаемых платформ (может, мобильное приложение).
	•	Постоянно применять данные мониторинга (Langfuse) и отзывы пользователей для улучшений архитектуры: например, улучшить алгоритмы выбора контекста (памяти) для снижения токенов или добавить механизмы для конфиденциальности данных (удаление пользовательских данных по запросу).

Каждый шаг логически опирается на предыдущий: начиная с минимального работающего продукта (шаги 2-3), мы постепенно добавляем “слои интеллекта” – память, инструменты, мульти-клиентность, наблюдение. Такой поэтапный подход позволяет выявлять и решать проблемы постепенно, обеспечивая к финалу прочную и масштабируемую архитектуру проекта.
